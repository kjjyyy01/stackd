## 제품 한 줄 (Day 1 재확인 + Day 2 확정)

설정을 붙여넣거나 골라 담으면 **공유하고 싶어지는 AI 스택 카드**가 나온다 — 한국어 UI, 영어 카드, 비로그인, DB·인증·저장소 0.

**생태계 범위 (grill Q8 확정)**: v1은 **Claude Code 생태계 한정** — 카탈로그·파싱·카피 전부 Claude Code 기준. 멀티 도구(codex·gemini 등)는 backlog. MCP는 도구 중립이라 타 도구 유저도 카드의 일부는 만들 수 있음(부수 효과, 설계 대상 아님).

## 핵심 플로우

홈 진입 → 스택 담기(검색·선택 기본) → 카드 미리보기·꾸미기(`card_create`) → PNG 다운로드/링크 복사(`card_share`) → 받은 사람이 링크의 "나도 만들기"로 재진입(`utm_source=card`) → 루프.

## SCR 목록 (5개 — 상한 7 이내)

> 컷 우선순위: 시간 부족 시 **SCR-02(파싱)부터** 컷. SCR-01·03·04는 확산 루프의 몸통이라 컷 불가.

### SCR-01 홈 (랜딩 + 스택 빌더) `/`

- **목적**: 가치 전달과 생성 시작을 한 화면에서 — 랜딩·빌더 분리는 전환 손실만 낳으므로 통합
- **구성**: 히어로(한 줄 가치 + 완성 카드 예시 1장) → 스택 빌더
  - 카탈로그 **검색·선택** (기본 경로): 스킬/플러그인/MCP/에이전트 카탈로그 100~200개 *(Day 3 피드백 2026-08-15: **개발 기술 스택** language/framework/tool 60~80개 추가 — 카테고리 4종→7종, 카드 2단)*, 카테고리 필터 + 텍스트 검색
  - **직접 입력** (카탈로그에 없을 때): 이름 + 카테고리만 입력하면 담김 — 카탈로그가 낡아도 서비스가 죽지 않는 안전판
  - 담은 스택 목록(선택 해제 가능) + "카드 만들기" CTA
- **상태**: 빈 상태(0개 선택 시 CTA 비활성 + 안내), 카탈로그는 정적 데이터라 로딩/실패 상태 없음
- **컷 여부**: 불가 (진입점)

### SCR-02 붙여넣기 파싱 (보조 입력 모드)

- **목적**: 설정 파일 텍스트를 붙여넣으면 스택 후보를 추출해 빌더에 채움 — 일일이 검색·선택하는 것보다 빠른 경로 (grill Q1: 속도 보완이 잔류 사유)
- **구성**: SCR-01 내 탭/모드 (별도 라우트 아님). textarea + "추출" → 인식된 항목을 선택 상태로 반영, 미인식분은 무시
- **대상 형식 (grill Q9 확정)**: **딱 2형식** — ① `settings.json`(enabledPlugins) ② `CLAUDE.md`(명시적 도구 언급). 그 외 텍스트는 "인식 못 함"으로 당당하게 처리 — 인식률 개선은 v1의 일이 아니라 실사용 데이터가 시킬 일
- **방식**: **클라이언트 정규식·휴리스틱 매칭** (AI API 아님 — 아래 판정 ③). 실패해도 검색·선택 경로가 살아 있으므로 서비스 생존
- **상태**: 추출 0건 시 "직접 골라 담기" 안내로 폴백
- **컷 여부**: **컷 1순위** — Day 1에서 보조로 강등된 기능. Day 9 판정 시 최우선 삭제 대상

### SCR-03 카드 미리보기 · 커스터마이즈 · 공유 `/card`

- **목적**: 제품의 승부처 — "공유하고 싶어지는" 비주얼이 여기서 결판
- **구성**: 카드 실시간 미리보기(영어 출력) + 템플릿 2~3종 선택 *(Day 3 변경: 시그니처 1종 고정 + 액센트 컬러 — docs/prd/21 OQ-001)* + 액션 2개(PNG 다운로드 / 공유 링크 복사) *(Day 3 추가: QR로 건네기 → 액션 3개)*
  - 카드 내용: **닉네임(필수 입력, 텍스트 1필드 — 계정·핸들 연동 없음, Day 2 검토 확정)**, 스택 목록(카테고리별), stackd.kr 워터마크
  - 카드 타이틀 = `{닉네임}'s AI Stack` — 닉네임이 타이틀의 소유격을 채우는 구조 (레이아웃 1벌)
  - **스택 12개 상한 (grill Q5 확정)**: 초과 시 빌더에서 "카드는 12개까지" 안내 — 자랑용 카드는 전부가 아니라 베스트를 담는 큐레이션. 숫자는 Day 3 카드 시안 보고 미세 조정 가능하되 상한 존재는 고정
  - PNG는 클라이언트 이미지 생성(구현 방식은 Day 3+), 이미지에는 워터마크가 "나도 만들기" 역할
- **이벤트**: 미리보기 도달 = `card_create`, 다운로드/링크 복사 = `card_share` (Day 3 스펙에서 확정)
- **상태**: 닉네임 미입력 시 다운로드·링크 복사 비활성 + 입력 유도 (미리보기는 placeholder로 표시), 이미지 생성 실패 시 에러 토스트 + 재시도
- **컷 여부**: 불가 (제품 본체)

### SCR-04 공유 카드 페이지 `/c` *(Day 3 확정: 라우트 `/stack`으로 변경 — docs/prd/04 참조)*

- **목적**: 확산 루프의 착지점 — 링크 받은 사람이 카드를 보고 "나도 만들기"로 진입
- **구성**: 공유된 카드 렌더 + "나도 내 스택 카드 만들기" CTA(→ `/?utm_source=card`)
- **방식**: 카드 상태를 **URL 쿼리/해시에 인코딩** (호스팅형 카드 URL은 backlog)
  - **페이로드 = 텍스트 자체 포함 (grill Q3 확정)**: 카탈로그 id 참조가 아니라 이름·카테고리 텍스트를 압축 인코딩(lz-string류) — 한 번 공유된 링크는 카탈로그가 어떻게 바뀌든 영원히 재현. 스택 12개면 압축 후 수백 자 = URL 한계(~2,000자) 안
  - **동적 OG 이미지 (grill Q2 확정)**: Next.js 내장 `ImageResponse`(next/og)로 URL 파라미터를 읽어 **카드별 OG 이미지를 동적 생성** — 카톡·X 미리보기에 그 사람의 카드가 보여야 링크 확산이 성립. 서버리스 함수 1개가 생기므로 백엔드 판정을 "DB·인증·저장소 0"으로 재정의 (아래 판정 ①)
- **악용 방어 (grill Q4 확정)**: 구조적 방어만 — 항목당 글자수·항목 수(12)·닉네임 길이 제한을 빌더와 `/c`·OG 렌더 전부에 적용. React 텍스트 렌더라 XSS 원천 차단, 저장·검색·갤러리가 없어 악성 카드는 만든 사람이 직접 뿌려야만 존재(확산 표면 좁음). 신고 기능은 갤러리(v2)와 함께
- **상태**: 파라미터 손상/누락 시 홈으로 안내 (에러 화면 아님)
- **컷 여부**: 불가 (킬 크라이테리아 `card_share`·`utm_source=card`의 전제)

### SCR-05 분석 고지 페이지 `/privacy`

- **목적**: GA4 사용 고지 — PLAN.md Day 15~16 "무조건 필수" 항목의 화면 몫을 미리 확정

## 범위 판정 3종

### ① 백엔드 판정 — **DB·인증·저장소 0 확정** (grill Q2로 재정의)

- 비로그인 + 클라이언트 이미지 생성 + URL 인코딩 공유 → 인증·DB·저장소 전부 불필요
- **유일한 서버 코드 = 동적 OG 이미지 함수 1개** (next/og `ImageResponse` — Vercel 내장, 고정비 0·운영 부담 0). "백엔드 0"의 취지(비용·복잡도 방어)는 유지되나 문구는 "DB·인증·저장소 0"이 정확
- 관리형 서비스(Supabase/Clerk)도 v1 미도입 → **Day 4~9 6일 전부 프론트** (백엔드 선배정 없음, OG 함수는 SCR-04 작업에 포함)
- 호스팅형 카드 URL(짧은 링크·조회수 등)은 저장소가 생기는 순간이므로 backlog 행
- 고정비 영향: DB 0원 — 월 상한 4만원 내 도메인+호스팅만

### ② 콘텐츠 소요 판정 — **1일 배정 (Day 4)**

- 카탈로그 100~200개: 공식 마켓플레이스 + awesome 리스트에서 수집 (이름·카테고리·한 줄 설명·출처) — **범위는 Claude Code 생태계 한정 (grill Q8)**: Cursor·Codex 전용 항목은 담지 않음
- Day 1 추산은 반나절이었으나 스키마 정의·중복 정리 포함 **Day 4 하루를 명시 배정** — 빌더 개발(검색·필터)이 이 데이터 스키마에 의존하므로 최우선 선행
- **수집 방식 (Day 4 실행 순서)**:
  1. **스키마 먼저 확정**: `id / name / category / description(영어 한 줄) / source(출처 URL)` 5필드 — category 체계가 곧 카드의 그룹핑이므로 수집 전에 결정
  2. **소스 우선순위**: 공식 레지스트리(Anthropic 스킬·플러그인, MCP 공식 레포) → awesome 리스트(awesome-claude-code 등) → 마켓플레이스 상위권만 선별
  3. **변환은 에이전트 작업**: 소스가 대부분 정형 마크다운(리스트·테이블)이라 스크래핑 코드 없이 Claude가 읽어 JSON으로 변환
  4. **정규화·중복 제거**: 여러 소스 중복 등장분을 이름 키로 병합 — **중복 등장 = 인지도**를 100~200개 컷 기준으로 사용 (전수 수집이 아니라 인기순 큐레이션)
  5. **검수 기준**: 본인 스택(0번 카드)이 카탈로그만으로 전부 담기는지 확인 — 안 담기면 수집 누락 신호
  6. **산출물**: `data/catalog.json` 정적 파일로 repo 커밋, 빌더가 import (fetch·API 없음, 수십 KB라 번들 포함 무해)
- v1은 정적 카탈로그로 고정 — 낡아도 직접 입력 경로가 안전판 (갱신 자동화는 backlog)
- 카드 템플릿 2~3종의 정적 디자인은 Day 4~9 개발에 포함, 비주얼 극대화는 Day 10~12 중점 축 몫
- 더미 데이터 런칭 리스크 없음 — 카탈로그가 곧 실데이터이고, 0번 카드(본인 세팅)가 예시 콘텐츠

### ③ 외부 API·AI 판정 — **v1 외부 API 0 확정**

- "AI 스택 카드"의 AI는 **소재이지 기능이 아님** — 생성·파싱 모두 클라이언트 로직, AI API 호출 없음
- SCR-02 파싱은 정규식·휴리스틱 — 실패 폴백은 검색·선택 경로 (이미 기본 경로라 폴백 비용 0)
- 따라서 비용 상한·레이트 리밋 결정 대상 없음, **pm-ai-shipping Day 15~16 재소환 불필요**
- AI 파싱(LLM으로 설정 해석)은 backlog 행 — 정규식 파싱의 인식률이 실사용에서 문제로 확인될 때만

## 시장 판정 — **국내 올인 (v1)**

Day 1의 "한국 우선, 글로벌은 보너스"를 **국내 올인으로 확정 상향** (Day 2 검토에서 결정):

- v1의 성공/실패 판정은 **100% 국내에서 난다** — 표본 300명·card_share 30명은 디스콰이엇·GeekNews에서 모은다
- **해외에 쓰는 자원 0**: Product Hunt 준비 안 함, 영어 런칭 포스트 안 씀, 영어 UI 안 만듦
- 카드 영어 출력은 유지 — 이건 시장 선택이 아니라 제품 속성 (스킬·도구명이 영어)
- 해외는 **측정만 한다**: GA4 지역 데이터에서 해외 유입 비율이 유의미하면, 그것이 i18n(영어 UI 토글, backlog)을 앞당기는 트리거

## 키워드-화면 매핑 판정 — **해당 없음** / 대표 키워드 — **확정**

- 목적: SEO가 아니라 **호칭 통일** — 커뮤니티에서 불리는 이름과 브랜드 검색("스택드", "AI 스택 카드") 대비
